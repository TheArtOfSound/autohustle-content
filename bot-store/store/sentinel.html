01 / What it does

Make failures visible.

Studio 0.9.3 separates Overview, Endpoints, Incidents, Notifications and Settings into five workspaces. Drafts survive navigation. Endpoint investigation shows retained check samples (not measured uptime); incidents show elapsed or resolved duration. Monitoring controls stay global. The monitoring and licensing APIs are unchanged.

Health dashboard

Add and edit endpoints, run immediate checks and review latency and status history.

Incident lifecycle

Track failures and recovery; filter open or resolved incidents without losing evidence.

Opt-in notifications

Consecutive failure thresholds, cooldowns and Discord, Telegram or Resend email adapters.

Local credentials and backups

Passphrase-encrypted credential vault and configuration-only backups. Credentials excluded from exports.

02 / First run

From download to first result.

  1. Install Node.js 22 or newer.

    Official Node.js download. No Bot.AutoHustle account required.

  2. Extract the complete ZIP.

    Keep all application modules together in a dedicated folder.

    Download evaluation ZIP ↓
  3. Launch the local application.

    Open a terminal in the extracted folder.

    node sentinel-studio.mjs

    Open http://127.0.0.1:4317/ on the same computer.

  4. Add an authorized endpoint.

    Run a check to establish its health, then start monitoring. No purchase or license needed for the five-endpoint evaluation.

Before you run

This ZIP includes all five 0.9.3 runtime modules. No native installer is included.

Vault-backed alerts require manual unlock after restarting. Environment credentials are supported separately.

Keep the terminal open while monitoring. Ctrl+C stops the process. Do not expose the local dashboard to the internet.

03 / Technical truth

What is verified — and what is not.

0.9.1 rejects concurrent writers using the same data directory and sends recovery alerts only to channel types with a previously accepted failure or reminder. Stop all earlier versions before reusing a data directory. If a crash leaves .sentinel-lock, remove it only after confirming all instances have stopped. Older incidents without recorded acceptance do not produce recovery alerts until a new alert is accepted. Changing destinations mid-incident may route a recovery to the new destination for the same channel type.

For 0.9.3, 30 interface harness, 21 core API and four hardening checks passed. The 134 local checks for 0.9.1 remain historical; the entire suite was not rerun. Live messaging receipt, long-running external monitoring, native Windows installation and independent security review remain outstanding. HTTP success does not prove a page renders correctly.
Monitoring and storage

HTTP status and latency, sequential checks, local records and incident history. Monitoring stops when the process is closed. No hosted uptime guarantee.

License and editions

0.9 supports offline test license activation: Evaluation 5 endpoints, Personal 25, Professional and Business 100. Existing endpoints continue after expiration or removal. Installation counts are not enforced. A separately configured trusted test public key is required; no production issuer or paid checkout exists.

Notifications and credential vault

Credentials can be supplied in the environment or stored in the encrypted vault. The vault requires manual unlock after restart; provider acceptance is not recipient receipt. See the vault guide and alert guide.

Privacy and backup

Configuration export excludes credentials and historical records. Stop the engine before backing up the entire data directory. Avoid secrets in endpoint names and URLs.
